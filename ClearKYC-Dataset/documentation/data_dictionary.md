# ClearKYC Data Dictionary

This document describes **every table and every column** of the ClearKYC database as it actually exists (PostgreSQL 17, Prisma schema `prisma/schema.prisma`, five migrations). It was produced from the live database catalogue, so the data types, required flags, defaults, constraints and indexes are exact; the descriptions and business rules were added by hand.

> All data in the system is **synthetic**. Personal identifiers (PAN, Aadhaar, document numbers, dates of birth) are stored encrypted and are never shown here: the example records mask them.

## How to read the tables

| Column heading | Meaning |
|---|---|
| **Field** | The real column name in PostgreSQL (snake_case). In code and Prisma the same field is camelCase (`customer_id` = `customerCode` for the customer business ID, otherwise `customer_id` = `customerId`). |
| **Data Type** | The PostgreSQL type. `TEXT` is free text; `TIMESTAMP(3)` is date and time to the millisecond, stored in UTC without a time zone; `DATE` is a calendar day. |
| **Required** | **Yes** = the database refuses an empty value and there is no default. **Yes (default …)** = always has a value, filled in automatically when not given. **No** = may be empty. |
| **Allowed Values** | The values the database accepts (taken from CHECK constraints) or the format pattern. A dash means any value of that type. |
| **Description** | What the field means in plain language. |
| **Validation** | The rules that protect the field: constraints enforced by the database (primary/foreign/unique keys, CHECKs, triggers) and rules enforced by the application. |

**Foreign key** = a column that must point at an existing row in another table. **ON DELETE RESTRICT** = the parent cannot be deleted while children exist; **CASCADE** = children are deleted with the parent; **SET NULL** = the link is cleared.

## 1. Customer

**Table:** `Customer` · **Rows in the current database:** 50 · **Primary key:** (id)

**Purpose.** A person (Individual) or an organisation (Company) that has been onboarded. Everything else in the system hangs off a customer.

**Business logic.**

* The business ID (`customer_id`, for example CUS-000001) is generated by the database sequence `customer_code_seq` through `next_customer_code()`. The client can never choose it, and a trigger stops it ever changing.
* Individuals must have a date of birth and an Aadhaar number and no company fields. Companies must have a registration number, business activity and incorporation date and no personal fields (CHECK `Customer_type_fields_check`).
* PAN and Aadhaar are stored **encrypted** (AES-256-GCM). Separate keyed hashes (`pan_hash`, `aadhaar_hash`) let the database refuse a duplicate customer without storing or searching plaintext. APIs only ever return masked values.
* `registration_status` is the onboarding status only. It is NOT the KYC completeness (that is calculated from documents) and NOT the risk level (that comes from the newest RiskRating).
* The customer's current risk level is not stored here: it is the newest `RiskRating` row.

## 3. KYCRequirement

**Table:** `KYCRequirement` · **Rows in the current database:** 25 · **Primary key:** (id)

**Purpose.** A rule saying which document a customer of a given type and risk level must provide. These are configurable sample business rules, not legal requirements.

**Business logic.**

* A requirement applies to a customer when its type and risk level match, it is active, and today falls inside `effective_from` – `effective_to`.
* Completeness = verified mandatory requirements ÷ mandatory requirements. Changing a requirement changes completeness immediately because completeness is always calculated, never stored.
* There is no business code on this table today: it is identified by its numeric `id`. (The required `KYC-2026-000001` format is not implemented; see `id_conventions.md`.)

| Field | Data Type | Required | Allowed Values | Description | Validation |
|---|---|---|---|---|---|
| `id` | INTEGER | Yes (auto) | — | Internal numeric key (auto-increment). Used by foreign keys; people see the business ID instead. | Primary key; unique; never reused |
| `customer_type_id` | INTEGER | Yes | — | The customer type this rule is for. | Foreign key to CustomerType(id), ON DELETE RESTRICT |
| `risk_level` | TEXT | Yes | Low, Medium, High | The risk level this rule is for. | CHECK: Low, Medium or High |
| `document_type` | TEXT | Yes | — | Name of the document required, e.g. PAN, Address Proof. | Not blank; compared by exact text with Document.document_type (there is no foreign key) |
| `is_mandatory` | BOOLEAN | Yes (default true) | — | Mandatory documents count towards completeness; optional ones do not. | Boolean |
| `effective_from` | DATE | Yes | — | First day the rule applies. | Required date |
| `effective_to` | DATE | No | — | Last day the rule applies. Empty = no end. | Not before effective_from (CHECK) |
| `is_active` | BOOLEAN | Yes (default true) | — | Switch to turn a rule off without deleting it. | Boolean; no two active rules for the same type, risk level and document may overlap in dates (application rule) |
| `created_at` | TIMESTAMP(3) | Yes (default now()) | — | When this requirement row was created (UTC). | Set by the database; not editable |
| `updated_at` | TIMESTAMP(3) | Yes | — | When this requirement row was last changed (UTC). | Maintained by the application on every update |

**Foreign keys:** `customer_type_id` → CustomerType(id) [RESTRICT].

**Indexes and uniqueness rules:**

* **Unique** (customer_type_id, risk_level, document_type, effective_from)
* (customer_type_id, risk_level, is_active)

**Table-level rules (CHECK constraints involving several columns):**

* `KYCRequirement_dates_check`: (effective_to IS NULL) OR (effective_to >= effective_from)

## 4. Document

**Table:** `Document` · **Rows in the current database:** 152 · **Primary key:** (id)

**Purpose.** A document record submitted for a customer. Only the metadata and a file reference are stored in PostgreSQL; the file itself lives in the upload folder.

**Business logic.**

* A new document is always created as `Pending` together with a first Verification row. Uploading never makes a document valid: only a reviewer's decision does.
* `status` is a copy of the NEWEST Verification row, kept in step by the trigger `Verification_sync_status`, so it can never disagree with the history.
* A document whose `expiry_date` is before today is **Expired** whatever its status says. An expired document never counts as valid verified evidence (see `expiry_configuration.md`).
* The same document cannot be submitted twice for the same customer (unique index on customer, type, number hash, issue date and submission date). The same number used by a DIFFERENT customer is not prevented by the database.
* Documents have no business code today: they are identified by numeric `id`. (The required `DOC-CUS-000001-001` format is not implemented.)

| `requirement_id` | INTEGER | No | — | The requirement this document was submitted against. Empty for extra evidence. | Optional foreign key to KYCRequirement(id), ON DELETE SET NULL |
| `document_type` | TEXT | Yes | — | Type of document, e.g. PAN, Photograph. | Not blank; must be a known type (application rule) |
| `document_number` | TEXT | No | — | The (synthetic) document number, **encrypted**. Shown masked. | Present together with its hash or both empty (CHECK) |

| `issue_date` | DATE | Yes | — | Date the document was issued. | Required; not after the submission date (CHECK) |

## 5. Verification

**Table:** `Verification` · **Rows in the current database:** 376 · **Primary key:** (id)

**Purpose.** One review decision about a document. This is the verification HISTORY: every decision is a new row.

**Business logic.**

* Rows are insert-only: triggers refuse UPDATE and DELETE, so history can never be rewritten. The newest row is the document's current status.
* A reviewer must be an active Reviewer or Admin (trigger `Verification_reviewer_authorised`). The system itself writes the first `Pending` row, with no reviewer.
* "Rejected" and "Requires Resubmission" must carry remarks. A document that has already expired cannot be set to Verified.

| Field | Data Type | Required | Allowed Values | Description | Validation |
|---|---|---|---|---|---|
| `id` | INTEGER | Yes (auto) | — | Internal numeric key (auto-increment). Used by foreign keys; people see the business ID instead. | Primary key; unique; never reused |
| `document_id` | INTEGER | Yes | — | The document this decision is about. | Foreign key to Document(id), ON DELETE RESTRICT |
| `reviewer_id` | INTEGER | No | — | Who made the decision. Empty only for the system-created Pending row. | Optional foreign key to Reviewer(id); required for every status except Pending (CHECK) |
| `status` | TEXT | Yes | Pending, In Review, Verified, Rejected, Requires Resubmission | The decision recorded. | CHECK: one of the allowed values |
| `remarks` | TEXT | No | — | Explanation of the decision. | Required (not blank) for Rejected and Requires Resubmission (CHECK) |
| `verification_date` | TIMESTAMP(3) | Yes (default now()) | — | When the decision was made. | Defaults to now; the data generator may set earlier dates |
| `created_at` | TIMESTAMP(3) | Yes (default now()) | — | When this verification row was created (UTC). | Set by the database; not editable |

**Foreign keys:** `document_id` → Document(id) [RESTRICT]; `reviewer_id` → Reviewer(id) [RESTRICT].

## 6. RiskRating

**Table:** `RiskRating` · **Rows in the current database:** 82 · **Primary key:** (id)

**Purpose.** One risk assessment of a customer. A customer is assessed many times; the newest row is the current rating, the older rows are history.

**Business logic.**

* The score is the sum of the points of all matching rules (customer type, country, business activity, occupation, simulated PEP/sanctions screening, owner risk for companies), capped at 100. Level: Low below 30, Medium 30–59, High 60 and above. The rules are prototype assumptions in `config/riskRules.js`.
* `risk_reasons` stores every reason and its points, so a score can always be explained and re-added.
* `assessment_status = Requires Manual Review` means a person must look. It is not a rejection and not a risk level: `risk_level` always stays Low, Medium or High.
* Rows are insert-only (triggers block UPDATE and DELETE). A level change is a new row whose `previous_risk_level` records the old level and also writes an audit event.

| `risk_score` | INTEGER | Yes | — | Total points, 0 to 100. | CHECK: between 0 and 100; equals the sum of the reasons' points capped at 100 (data quality check) |
| `risk_level` | TEXT | Yes | Low, Medium, High | Risk band calculated from the score. | CHECK: Low, Medium or High; must match the configured score bands (data quality check) |

## 7. BeneficialOwner

**Table:** `BeneficialOwner` · **Rows in the current database:** 40 · **Primary key:** (id)

**Purpose.** An individual who ultimately owns or controls a COMPANY customer, with their share. In the current design one row is one person-in-one-company (see `ownership_model.md`).

**Business logic.**

* The owner can only be attached to a Company customer (trigger `BeneficialOwner_company_only`).
* Ownership is calculated separately for each company: the sum of the percentages of that company's rows. Exactly 100% = reconciled; below = incomplete; above = problem; no rows = no owners.
* Date of birth is personal data and is stored **encrypted**; lists show only the birth year.
* The same real person owning two companies is currently two rows (the unique index is per company), which duplicates their personal data and their screening history. There is no bridge table and no effective-date history on the percentage (changes overwrite the row, and the audit trail records the old and new value).

## ReviewSchedule (additional entity: periodic KYC reviews)

**Table:** `ReviewSchedule` · **Rows in the current database:** 50 · **Primary key:** (id)

**Purpose.** When a customer's next periodic KYC review is due. One row per review cycle, so a customer keeps their full schedule history.

**Business logic.**

* Interval by risk level (illustrative): Low 36, Medium 24, High 12 months. next_review_date = last_review_date + interval.
* Completing a review closes the row (Completed) and starts the next cycle. A risk change supersedes the row and re-bases the interval.
* Only one Scheduled row per customer (partial unique index). Non-current rows are frozen by a trigger.

| Field | Data Type | Required | Allowed Values | Description | Validation |

| `risk_level` | TEXT | Yes | Low, Medium, High | Risk level that decided the interval. | CHECK: Low, Medium or High |
| `last_review_date` | DATE | Yes | — | Date of the previous review (onboarding counts as the first). | Required date; not in the future for the current row |
| `next_review_date` | DATE | Yes | — | Date the next review is due. | After last_review_date (CHECK); equals last + interval (data quality check) |
| `review_interval_months` | INTEGER | Yes | — | Months between reviews. | Between 1 and 120 (CHECK) |

**Indexes and uniqueness rules:**
